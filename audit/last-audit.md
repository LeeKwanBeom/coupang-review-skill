## 결함 1 — 수정함 (동기화 규칙 1 `too_old` 제거)

**경위(다음 회차가 다시 판정하지 않도록 남김):** API `startDateTime` 은 **리뷰 작성일
(`createdAt`)** 로 거르고, 엑셀 `날짜` 열은 **주문일(`orderedAt`)** 이다. 두 필드가 서로
다르다는 것을 1회차 실측으로 확인했다(`createdAt` 최소값 = startDate, `orderedAt` 최소값은
07-15~07-21, 580건 중 58건이 주문일만 범위 밖). 저장 스크립트의 규칙 1 은 `날짜` 열로
"범위 밖"을 판정했기 때문에 그런 리뷰가 매 회차 삭제→재추가됐다.

**선택:** `too_old` 를 **제거**했다(`too_old and missing` 으로 좁히는 안 대신). 이유:
`if (too_old and missing) or missing` 은 `if missing` 과 논리적으로 같다 — `missing` 이
범위 밖·삭제·4~5점 수정을 전부 잡으므로 날짜 규칙은 어느 형태로든 아무 행도 추가로
지우지 못하고 오보고만 만든다. 남겨 두면 다음 사람이 "무슨 역할이지" 하고 또 읽는다.
`cutoff`·`months_back()`·`calendar` import 도 쓸 곳이 없어져 같이 뺐다. `parse()` 는
정렬에 계속 쓴다.

- 위치: Step 3 "동기화 정책" 문단 / 3-2 저장 스크립트 행 분류 루프 (`missing` 만 남음)
- 문서: "1. 날짜가 오늘 기준 1개월보다 이전 (수집 범위 밖) / 2. …" 두 항목을 "이번 수집
  결과에 주문번호가 없는 행을 삭제" 한 항목으로 바꾸고, 날짜 열로 판정하지 않는 이유
  (필터 기준 ≠ 날짜 열)를 문단으로 적었다.
- **하지 않은 것:** `날짜` 열을 `orderedAt` → `createdAt` 으로 바꾸는 것. 사용자 결정
  사항이고 기존 엑셀 전체에 영향이 간다. **선택지로 남긴다** — 바꾸면 열 이름이 "리뷰
  작성일"이 되고 엑셀의 날짜와 API 범위가 일치하게 된다. 바꾸지 않으면 주문일이 범위
  밖인 행이 엑셀에 계속 보이는데, 그건 리뷰가 범위 안이므로 정상이다.
- 실측(엑셀 **사본**, 실제 파일 md5 `a1b9827c…` mtime 03:15 그대로):
  - T1 수정 전 스크립트 / 원본 사본 → `{"new":1,"deleted":1,"rows":5}` (결함 재현)
  - T2 수정 후 스크립트 / 원본 사본 → `{"new":0,"deleted":0,"rows":5}`
  - T3 수정 후 / 가짜 행 2개(참 제육 `FAKE01` 2026-08-20 범위 안, `FAKE02` 2026-07-01
    범위 밖 — 둘 다 이번 수집에 없음) → `{"new":0,"deleted":2,"rows":5}`, 남은
    주문번호 5개는 실제 저점수와 일치. **삭제 기능은 살아 있다.**
  - T4 수정 후 / 가짜 행 2개 + 참 제육 `ok:false` → `{"deleted":0,"untouched_rows":3}`,

## 결함 3 + 개선안 1 — 수정함 (API 오류 봉투 처리)

- Step 2 `page()`: `r.json()` 직후 `'code' in j && j.code !== 'SUCCESS'` 면
  `{ ok:false, apiError:true, error:'API 오류 <code>: <error.message>' }` 를 즉시 반환
  (재시도 없음). `code` 필드가 없는 응답은 종전대로 `data ?? result ?? j` 로 다룬다.
- Step 2 `one()`: p1 실패 사유에 `first.apiError ? first.error : 'p1 실패 ' + first.error`
  — API 오류는 서버 메시지를 그대로 `reason` 으로 쓴다. 2페이지 이후의 API 오류는
  종전대로 `failedPages` 에 들어가 `페이지 실패 pN` 으로 `ok=false` 가 된다(변경 없음).
- 트러블슈팅 표: `API 오류 <code>: <message>` 행 신설(10001·10007 실측 메시지 포함),
  `응답 구조 불명` 행의 원인·대응을 "code 없는 스키마 변경 / 봉투 키가 보이면 위 행"
  으로, `apiTotal=0인데 화면엔 리뷰가 보임` 행을 "statusType 오류는 0 이 아니라
  `API 오류 10007` 로 나타난다" 로 고쳤다.
- 실측: 존재하지 않는 storeId(1)로 수정된 `page()`/`one()` 을 돌려
  `reason = "API 오류 10001: 상점 정보를 찾을 수 없습니다."` 확인(로그에도 같은 문장).
  WAF(size 변경) 실험은 하지 않았다.
- `ok` 판정 조건은 완화하지 않았다 — 실패 경로가 하나 더 생겼을 뿐이다.

## 점검표 개정안

1. **설치본 경로 오류.** 점검표 39·51행과 README 의 `/mnt/skills/plugins/coupang-review/SKILL.md` 는 이 환경에 없다. 실제는 `/root/.claude/skills/synced/<id>/coupang-review/SKILL.md` (스킬 호출 시 "Base directory" 로 표시됨). md5 명령을 "스킬 호출 시 표시되는 Base directory 아래 SKILL.md" 로 바꿀 것
2. **백업 위치.** `$HOME/skillwork` 는 세션별 홈이라 세션이 끝나면 접근 불가(실측). 점검표 68~70행의 백업 지시를 사용자 폴더 안(`$HOME/mnt/claude/backup/`)으로 바꿀 것. 이번 회차 백업은 세션과 함께 사라진다 — 단 Step 3 을 안 돌려 실제 파일은 변경 없음
3. **상충 지시.** B 항목 "`size=5` 외의 값이 정말 403 인지 한 번만 실측" 과 판정 기준 "실제 엑셀과 WAF 는 건드리지 마라" 가 충돌. 이번엔 1회 실측(403 확인, 직후 정상)으로 처리. 한쪽으로 정리할 것 — 매 회차 403 을 확인할 필요는 없어 보임(기준선에 기록됐으니 "변경 의심 시에만" 으로)
4. **"되돌리면 안 되는 것" 표의 잘림 행** "한 번에 읽으면 약 1,000자에서 조용히 잘려" → "`[TRUNCATED]` 표식과 함께 잘려" 로. 실측 수치 항목(A) 의 "1,214자 / 7건" 도 이번 "1,243자 / 5건" 으로
5. **매 회차 통과만 나는 항목.** A "window.__API__ Step 1→2 인계" — Step 2 에 `|| '/api/v1/…'` 폴백이 있어 끊겨도 동작한다. 제거 후보
6. **배민에서 옮겨온 것 중 해당 없음.** E "배민의 `blocked` 집계처럼 `collected + α === apiTotal`" — 쿠팡 API 엔 blocked 개념이 없고 오늘 `collected === apiTotal` 정확 일치. 대신 "API 필터 기준(`createdAt`) vs 엑셀 날짜열(`orderedAt`) 일치 여부" 를 대조 항목으로 넣을 것
7. **신규 대조 항목.** "API 가 HTTP 200 + `code`≠SUCCESS 로 오류를 돌려주는 경우 스킬이 어떻게 보고하는지" 와 "응답 최상위 키·리뷰 키 목록(이번 기록) 과의 차이"
8. **계측 허용 범위 명시.** 이번에 Step 2 원문에 audit-only 1줄(`window._all`)을 넣어 원본 배열을 분석했다. 허용할지, 허용하면 "판정 로직은 건드리지 않는다" 조건을 점검표에 적을 것
9. **사본 dry-run 허용 명시.** 저장 스크립트를 엑셀 사본에 돌리면 실제 파일을 건드리지 않고 Step 3 을 검증할 수 있다(이번 결함 1 재현에 쓰임). "Step 3 은 실행하지 마라" 를 "실제 파일 대상으로는 실행하지 마라, 사본 dry-run 은 한다" 로
