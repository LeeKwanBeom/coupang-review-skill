# coupang-review 정기 점검표 (정본)

이 파일이 점검 절차의 정본이다. 사용자는 짧은 지시만 붙여넣고,
실제 절차는 이 파일을 읽어서 수행한다.

**이 파일은 매 회차 갱신된다.** 점검이 끝나면 "점검표 개정안"에서 사용자가
채택한 것만 반영하고 `audit/last-audit.md` 와 함께 올린다.
커밋 규칙은 아래 [마무리] 절을 따른다 — **이 머리말과 그 절은 항상 같은 말을
해야 한다.** 한쪽만 고치면 다음 회차가 틀린 지시를 먼저 읽는다.
채택 여부를 묻기 전에 고치지 마라.

버전: v2 (2026-09-09 — 1회차 점검 개정안 10건 반영. v1: baemin-review 점검표를 이 스킬 구조에 맞춰 옮김)

---

아직 고치지 말고 진단만. 뭘 고칠지는 사용자가 고른다.

[시작 전 확인 ① — 토큰부터 확보한다]

**진단을 시작하기 전에 push 토큰을 먼저 요청해라.** 마무리에 저장소로 두 파일을
올려야 하는데, 진단이 다 끝난 뒤에 요청하면 그 사이 세션이 끊길 때 결과가
통째로 유실된다. 다른 스킬 점검에서 실제로 그렇게 한 세션이 날아갔다.

요청 문구에 토큰이 안 보이면 **첫 응답에서** 이렇게 물어라:

> 점검을 시작하겠습니다. 마무리에 기준선과 점검표를 올려야 해서
> `coupang-review-skill` push 토큰(Contents: Read and write)이 필요합니다.
> 지금 주시면 진단 후 바로 올리고, 없으면 파일로만 드리겠습니다.

토큰 없이 진행하기로 했으면 진단 도중에도 중간 산출물을 파일로 먼저 내려주고
마지막에 다시 알려라. **토큰은 대화에 남으니 채팅 보고의 마지막 줄에 "GitHub 에서
폐기해 달라"고 반드시 적어라** — 지시문에 토큰이 그대로 들어온 회차(1회차)가 있었다.

[시작 전 확인 ② — 정본이 두 곳에 있다. 어느 쪽이 최신인지부터 확인해라]

**부트스트랩 방식이 아니다.** 저장소는 기록 보관소이지 실행 경로가 아니다.

| 무엇 | 어디 | 역할 |
|---|---|---|
| 실행 본문 | 설치본 — 스킬 호출 시 표시되는 **Base directory** 아래 `SKILL.md` | 스킬이 실제로 읽고 도는 것 |
| 사본·정본 | 저장소 `SKILL.md` | 수정은 여기서 하고 `.skill` 로 패키징 |
| 점검표·기준선 | 저장소 `audit/` | 이 파일과 회차 기록 |

- **설치 경로는 세션마다 패키지에서 다시 풀린다.** 거기에 쓴 것은 보존되지 않는다.
  고친 내용을 남기려면 저장소에 push 하고, `.skill` 로 다시 패키징해
  **사용자가 Claude 설정에서 재업로드**해야 실행에 반영된다.

**시작하면서 둘을 대조해라.** 설치본 경로는 환경마다 다르다 — `/mnt/skills/plugins/…` 는
Cowork 클라우드 세션에 없고(1회차 실측), 그 세션에서는
`/root/.claude/skills/synced/<id>/coupang-review/SKILL.md` 였다. 경로를 짐작하지 말고
**스킬 호출 시 화면에 찍히는 "Base directory" 줄의 경로**를 쓴다.

```bash
git clone https://github.com/LeeKwanBeom/coupang-review-skill
md5sum coupang-review-skill/SKILL.md "<Base directory>/SKILL.md"
```

- **md5 동일** → 정상. 그대로 진행한다.
- **다름** → 어느 쪽이 최신인지 판정하고 **그 사실부터 보고해라.**
  저장소가 최신이면 "재업로드가 안 된 것"이고, 설치본이 최신이면
  "저장소에 push 가 안 된 것"이다. 둘은 대응이 다르다.
  진단은 **저장소 사본을 기준으로** 하되, 설치본과 다른 부분은 따로 적어라.

[시작 전 확인 ③ — 실제 실행 없이는 진단이 절반이다]

이 스킬은 브라우저 안에서 내부 API 를 호출한다. 문서를 읽는 것만으로는
필드명이 아직 맞는지, `size=5` 가 여전히 유효한지, 응답 스키마가 그대로인지
판정할 수 없다. **사용자가 정한 방침이기도 하다: "개선 후 실제 사이트에서 실행 테스트".**

그러므로 이 점검은 **실제 1회 실행을 포함한다.** 다만 조건이 있다.

- **엑셀을 먼저 백업해라.** 이 스킬은 스냅샷 동기화라 실행이 기존 행을 지운다.
  백업은 **사용자 폴더 안** `$HOME/mnt/claude/backup/` 에 날짜·시각이 붙은 이름으로
  둔다(`mkdir -p` 로 만든다). `$HOME/skillwork` 같은 `$HOME` 아래는 세션별 홈
  (`/sessions/rcw-<세션id>/`)이라 세션이 끝나면 접근할 수 없다 — 1회차에서 그렇게
  둔 백업이 세션과 함께 사라졌다. SKILL.md Step 0 에도 같은 백업 단계가 있다(v2).
- **Step 3(엑셀 저장)은 실제 파일 대상으로는 실행하지 마라. 사본 dry-run 은 한다.**
  Step 0~2 와 결과 읽기까지 한 뒤, 3-1 JSON 을 기록하고 3-2 저장 스크립트를
  **엑셀 사본**(`cp` 해 둔 파일)에 돌려 `new/deleted/rows` 를 본다. 실제 파일의
  mtime·md5 가 그대로인지 끝에 확인해라. 1회차에서 이 방식으로 결함 1 을 재현했다.
- 브라우저·로그인이 준비돼 있지 않으면 사용자에게 요청하고 기다려라.
  배민과 달리 계정 전환은 없다. 쿠팡이츠 스토어 한 계정으로 3매장이 다 보인다.
- **audit-only 계측은 1줄까지 허용한다.** 원본 수집 배열이나 타이밍을 남기려고
  Step 2 스크립트에 `window._all[store.name] = all` 같은 대입 한 줄을 넣는 것은
  된다. 단 **판정 로직(`ok`·`reason`·`pick()` 후보·페이지 루프)은 건드리지 않는다.**
  넣은 줄은 기준선 "실행 실측 기록"에 그대로 적어라.

실행이 불가능하면 그 사실을 명시하고 **실행으로만 확인되는 항목을 전부
[추론]으로 표시해라.** 문서만 읽고 "필드명이 맞다 / API 가 정상이다" 라고 쓰지 마라.

[0단계 — 기준선 대조. 신규 진단보다 이걸 먼저]

저장소의 `audit/last-audit.md` 를 먼저 읽어라. 이게 정본이다.
없으면 "기준선 파일 없음"이라고 명시하고 (3)으로 넘어가라.

(1) 거기 적힌 항목을 지금 실물에서 하나씩 다시 확인해라.
    해결됨 — 수정 내용이 실물에 있다 (수정된 원문 인용)
    미해결 — 예전 상태 그대로다 (지금 원문 인용)
    근거없음 — 그때 지적 자체가 실물 근거가 없었다 (한 줄 사유)
    요약하지 말고 원문을 붙일 것.

(2) **저장소와 설치본이 어긋났는지 양방향으로 확인해라.**
    - 사용자가 재업로드를 안 했으면 → 지난 회차 수정이 설치본에 없다
    - 설치본에는 있는데 저장소에 없으면 → push 가 안 된 것이다
    지난 회차 기준선에 "수정함"으로 적힌 항목이 설치본에 없으면,
    **재업로드가 안 된 것이지 수정이 실패한 게 아니다.** 그 구분을 명확히 적어라.

(3) 그다음에 기준선에 없던 신규 항목만 찾아라.

[의도된 동작 — 결함으로 올리지 마라]

아래는 사용자가 알고 선택한 것이거나 SKILL.md "설계 근거"에 이유가 적힌 것이다.
"고치면 좋겠다"는 생각이 들어도 결함이 아니다. 바꾸려면 사용자 승인이 필요하다.

- **엑셀이 스냅샷 방식이라 조회 기간 밖 과거 리뷰가 지워진다.**
  사용자가 알고 선택했다. 이 엑셀은 누적 아카이브가 아니라 최근 현황판이다.
- **`size=5` 고정.** 다른 값은 WAF 가 403 을 돌려준다. 페이지가 많아 느려도
  바꾸지 않는다.
- **매장·페이지 모두 순차 호출.** 병렬로 부르면 API 가 잘못된 `total` 을 반환한 전력이 있다.
- **DOM 이 아니라 API 를 쓴다.** 쿠팡이츠 API 는 same-origin 이라 된다.
  배민 방식(DOM 스크롤)을 이식하려 하지 마라 — 두 스킬의 구조가 다른 이유다.
- **조회 기간은 최근 1개월.** 월말 overflow 는 해당 월 마지막 날로 클램핑한다.
- **결과를 매장 단위로 나눠 읽는다.** 반환값이 약 1,000자에서 조용히 잘린다.
- **엑셀은 플랫폼별로 분리한다.** 배민과 합치지 않는다.
- **날짜는 `YYYY-MM-DD`.** 배민 스킬과 통일한 형식이다.
- **`STATUS:403` 은 중단 조건이 아니다.** WAF 제약일 수 있어 Step 2 로 진행한다.

과거에 사고를 냈던 것들이다. 되돌아가 있으면 그 자체가 결함이다.

| `ok` 플래그 기본값이 실패 | 저장 스크립트의 `ok_stores` 필터를 빼면 실패 매장이 빈 배열로 동기화돼 저점수가 통째로 사라짐 | Step 2 `fail()` · Step 3-2 |

| 수집은 백그라운드 + 폴링 | 동기로 기다리면 45초 CDP 타임아웃에 걸림 | Step 2 · 완료 폴링 |

[특히 이런 걸 찾아줘]

■ A. 문서와 코드가 어긋나는 곳
   - 매장 정보 표(storeId 3개)가 실제 URL·응답과 맞는지
   - 트러블슈팅 표의 증상·원인·대응이 실제 코드 동작과 맞는지
   - 실측 수치가 지금도 유효한지. 현재 기준: 전체 `_res` JSON 1,243자 / 저점수 5건
     (2026-09-09), 매장별 325·305·609자, 저점수 1건당 97~162자. 낡았으면 갱신 대상
   - Step 간 값 인계(`apiTotal`·`ok`·`authExpired`·`failedPages`)가 끊기는 지점
   - **API 필터 기준과 엑셀 `날짜` 열이 같은 필드인지.** 1회차 실측: API 는
     `createdAt`(리뷰 작성일)로 거르고 엑셀 열은 `orderedAt`(주문일)이다. 이 차이
     때문에 생긴 결함 1 을 수정 회차에서 고쳤다. `createdAt` 최소값이 `startDate` 와
     같은지로 필터 기준이 그대로인지 본다

■ B. API 응답 스키마가 현재와 맞는지  ※ 실행으로만 판정 가능
   - `pick()` 후보들이 실제 응답에 존재하는지:
     `total`/`totalCount`/`totalElements` · `content`/`reviews`/`items`/`list` ·
     `rating`/`score`/`starCount` · `comment`/`reviewContent`/`content`/`text` ·
     `orderedAt`/`orderDate`/`createdAt`/`reviewedAt` ·
     `abbrOrderId`/`orderId`/`shortOrderId`/`orderNo` ·
     `orderInfo`/`items`/`menuInfo`/`orderItems`
   - **실제 응답의 최상위 키 목록을 그대로 보고하고, 직전 기준선의 목록과 대조해라.**
     기준선(2026-09-09): 최상위 `data, error, code` / `data` 아래 `content, pageNumber,
     pageSize, total` / 리뷰 18키. 후보에 없는 새 필드가 있으면 그것도 적어라.
   - **API 가 HTTP 200 + `code`≠`SUCCESS` + `error.message` 로 오류를 돌려주는 경우**
     스킬이 `API 오류 <code>: <message>` 로 보고하는지. 존재하지 않는 storeId(예: 1)로
     한 번 돌려 확인한다(실측 기준: `10001 상점 정보를 찾을 수 없습니다.`). 이건 WAF 와
     무관해서 매 회차 해도 된다.
   - `statusType=EXPOSE` 가 여전히 유효한지. 값이 틀리면 `apiTotal=0` 이 아니라
     `API 오류 10007` 로 나타난다(1회차 실측). 3매장 모두 `apiTotal=0` 이면 날짜
     파라미터 쪽을 의심한다.
   - `size=5` 외의 값이 403 인지는 **변경 의심 시에만** 실측한다(기준선에 2026-09-09
     `size=10 → 403` 이 기록돼 있다). 평소엔 WAF 를 건드리지 마라 — 아래 판정 기준의
     "WAF 는 건드리지 마라" 와 같은 뜻이다.

■ C. 조용한 실패가 가능한 경로
   이 스킬의 최대 위험은 "조용히 0건"이다. 아래를 코드에서 짚어라.
   - `apiTotal === null` 일 때 `MAX_PAGES=200` 상한에 걸리면 어떻게 되는지.
     상한에 걸린 것과 정상 종료를 구분하는 장치가 있는지
   - `failedPages` 가 있는데도 저장 단계로 넘어가는 경로가 있는지
   - `ratingFail` 이 전건일 때만 실패로 잡는데, 절반이 실패해도 통과하는 게 맞는지
     ※ 판단이 갈리면 결함이 아니라 개선안으로
   - `orderNo` 보조키(`NOKEY_날짜_메뉴`)가 회차마다 달라져 중복 행을 만들 수 있는지
   - 결과 읽기에서 잘림이 일어났는데 눈치채지 못하는 경로

■ D. 검증이 비어 있는 구간  ※ 결과는 전부 개선안으로 분류
   - `collected` 와 `apiTotal` 이 정확히 같은지 검증하는 장치(98% 기준만 있다)
   - 저장 후 엑셀을 다시 열어 행수·형식을 확인하는 단계가 없다
   - 3개 매장 결과를 합칠 때 `storeName` 오타를 잡는 장치가 없다
   - 백업 자동화(스냅샷 방식이라 실행 전 백업이 사실상 필수인데 절차에 없다)
   - 폴링 40회 상한에 걸렸을 때의 처리

■ E. 자동화·구조 개선 후보  ※ 결과는 전부 개선안으로 분류
   - 배민 스킬과 공유 가능한 부분(엑셀 저장 로직·날짜 정규화·`ok` 판정)
   - 매장 정보를 문서 본문이 아니라 별도 설정으로 뺄지
   - `collected === apiTotal` 정확 일치를 보고에 올릴지(1회차엔 3매장 모두 정확 일치.
     쿠팡 API 엔 배민의 `blocked` 같은 제외 집계가 없어 α 는 0 이어야 한다)

[판정 기준]

- 결함으로 올리기 전에 스스로 반증을 한 번 시도해라. "이게 사실은 문제가 아닌
  이유"를 찾아보고, 못 찾았을 때만 올려라. 특히 위 "의도된 동작" 목록을 먼저 봐라.
- **"특정 조건에서 반드시 틀려진다"고 쓸 거면 그 조건을 실제로 만들어서 보여줘라.**
  이 스킬은 브라우저에서 조건을 만들 수 있다 — `pick()` 후보를 임시로 비워
  `apiTotal: null` 경로 태우기, 존재하지 않는 storeId 로 응답 확인하기 등.
  못 만들었으면 결함이 아니라 개선안이다.
  **단 실제 엑셀과 WAF 는 건드리지 마라.**
- **실측한 것과 문서를 읽고 추론한 것을 구분해라.** 결함 표에 [실측]/[추론] 표시를
  달고, 추론만으로 올린 항목은 왜 실측하지 못했는지 한 줄로 적어라.
- **개수를 적을 때는 세어서 적어라.** "결함 4건" 처럼 숫자를 쓸 거면 실제로 세라.
  기록의 숫자가 틀리면 다음 회차가 그걸 기준으로 판정한다.
- **기록 문구는 방향·범위·개수를 원문에서 확인하고 적어라.** 코드는 맞는데
  문구만 틀린 오류가 다른 스킬 점검에서 반복해서 나왔다.
- **결함을 지적할 때는 지금 보고 있는 파일의 행 번호 + 원문을 인용해라.**
  다만 **수정 기록에는 절 이름·함수명으로 적어라.** 행 번호는 수정으로 밀리는데,
  밀린 번호가 실재하는 다른 줄을 가리키면 조용히 틀린다.
  행 번호를 병기할 거면 몇 행짜리 파일 기준인지 반드시 붙여라.

[이 점검표 자체도 점검 대상이다]

이 점검표는 baemin-review 점검표를 옮겨 만든 것이라 이 스킬에 안 맞는 부분이
있을 수 있다. 마지막에 따로 보고해라.

- 점검표가 시키지 않았는데 실물을 보다가 확인이 필요했던 것
- 점검표가 잘못 전제하고 있는 것 (파일 경로, 실측 수치, 의도된 동작 목록,
  "되돌리면 안 되는 것" 표의 위치 표기 등)
- 매 회차 통과만 나서 실효가 없는 항목
- 배민에서 옮겨 오면서 이 스킬엔 해당 없는 절차

이건 결함·개선안 어디에도 넣지 말고 "점검표 개정안"으로 따로 내라. 개수 제한 없다.

[지적 채택 규칙 — 개수보다 이게 중요하다]

- 지적하려면 **행 번호 + 문제되는 원문**을 인용해야 한다. 인용할 수 없으면
  지적하지 말고 통과 처리해라. 인용을 못 해서 제외한 항목이 몇 개인지
  마지막에 숫자로 알려줘.
- 아래 둘을 한 목록에 섞지 마라. 분리해서 따로 내라.
  결함 : 지금 이미 틀렸거나, 특정 조건에서 반드시 틀려지는 것
  개선안 : 있으면 좋은 것 / 자동화 후보 / 검증이 비어 있는 구간
  D·E 는 성격상 전부 개선안이다.
- 개선안은 최대 5개. 매번 새로 만들어내지 말고, 기준선에 이미 적힌 개선안이
  있으면 그걸 다시 쓰고 순위만 갱신해라.

[결과 정리 방식]

결함을 심각도 순으로, 항목마다:
- 지금 이미 틀렸는지 / 앞으로 틀려질 건지 (틀려진다면 언제)
- 실측으로 확인한 건지 추론인지
- 고치면 실제로 뭐가 달라지는지
- **작업 경로. 세 단계이고 하나라도 빠지면 미완이다:**
  · 저장소 `SKILL.md` 수정 → push
  · 그걸로 `.skill` 재패키징
  · **사용자가 Claude 설정에서 재업로드**
  재업로드 전에는 실행에 반영되지 않는다. 결과에 그 사실을 반드시 명시해라.
  저장소만 고치고 "완료"라고 하지 마라.

[수정 회차에 적용할 것 — 이 절은 진단이 아니라 다음 단계용이다]

이번 회차는 진단만 한다. 다만 여기서 나온 결함을 **고칠 때** 아래를 지켜야
같은 회차 안에서 새 결함이 생기지 않는다. 진단 보고서 끝에 이 절을 그대로
옮겨 적어 다음 단계가 읽게 해라.

- **수정은 저장소 `SKILL.md` 에서 한다.** 설치본을 직접 고치면 세션이 끝나며
  사라진다. 저장소에 push 한 뒤 그것으로 패키징해라.
- **한 번의 수정 → 한 번의 패키징 → 한 번의 재설치.**
  중간에 다른 세션을 열면 그 세션은 옛 캐시를 읽고 그 위에 수정한다.
  먼저 한 수정이 조용히 사라진다.
- **수정 후 반드시 파일을 다시 열어 눈으로 확인하고 나서 "완료"라고 말해라.**
  사용자가 정한 상시 방침이다.
- **고친 뒤 실제 사이트에서 1회 실행해라.** 사용자가 정한 방침이다.
- **같은 개념을 두 곳에서 고칠 때는 기준을 대조해라.** 이 문서는 설계 근거·
  코드·트러블슈팅 표에 같은 규칙이 세 번 나오는 곳이 있다. 한 곳만 고치면 어긋난다.
- **판정 조건을 완화하는 수정을 했으면 원래 잡히던 실패가 여전히 잡히는지
  다시 확인해라.** `ok` 판정과 `apiTotal` 관련이 특히 그렇다.
- **"되돌리면 안 되는 것" 표에 있는 것을 건드렸으면 그 표도 같이 갱신해라.**
- **수정 기록은 행 번호 대신 절 이름·함수명으로 적어라.**
- **수정과 검증은 다른 세션에서 한다.** 진단한 쪽이 수정하지 않고, 수정한 쪽이
  검증하지 않는다.

[검증 회차 — 수정이 끝난 뒤에 쓴다. 진단 회차에는 읽지 마라]

수정이 끝나면 **다른 세션에서** 검증을 받는다. 사용자가 아래 문구를 붙여넣으면 된다.
회차 이름을 박지 말고 "가장 최근 후속 조치 절들" 로 가리켜야 다음 회차에도 쓸 수 있다.

```
/coupang-review
방금 회차에 고친 것들이 실제로 반영·동작하는지 검증만 해줘. 새로 고치지는 마.
저장소를 받아 audit/last-audit.md 의 가장 최근 "수정 회차" 절들을 읽고,
거기 적힌 항목을 하나씩 실물에서 확인해라.
- 코드·문서가 실제로 그렇게 바뀌었는지 (절 이름 + 원문 인용)
- 적혀 있는 실측 근거가 그대로 재현되는지 (안 되면 그 사실을 보고)
- 기록의 숫자·방향·범위가 코드와 맞는지 (문구 오류는 코드만 봐선 안 잡힌다)
- 설치본과 저장소 md5 가 다르면, 재업로드 전이라 정상인지 확인만 하고
  결함으로 올리지 마라.
실행 전에 엑셀을 백업하고 Step 3(엑셀 저장)은 실행하지 마라.
재현 안 되는 항목이 있으면 그것만 알려줘. 판단은 내가 한다.
토큰은 주지 않는다. 검증만 하고 저장소에 아무것도 올리지 마라.
재패키징·재업로드도 하지 마라.
git clone https://github.com/LeeKwanBeom/coupang-review-skill
```

**수정하면서 원래 제안을 바꿨으면 기준선에 그 사실과 이유를 반드시 남겨라.**
검증이 그 대목만 따로 볼 수 있어야 한다.

[마무리 — 기준선 갱신]

진단이 끝나면 저장소의 아래 두 파일을 갱신해 올린다.

1. `audit/last-audit.md` — 아래 형식. 직전 회차 기록은 파일 아래쪽에
   "이전 기록" 으로 원문 보존해라.
2. `audit/checklist.md` — 이 파일. "점검표 개정안"에서 **사용자가 채택한 것만**
   반영하고 머리말의 버전 줄을 갱신해라. 채택 여부를 묻기 전에 고치지 마라.

**커밋은 두 번이다.** 진단 회차에 `last-audit.md` 를 먼저 올리고, 사용자가
개정안을 채택한 뒤 `checklist.md` + `last-audit.md` 정정분을 2차로 올린다.
개정안 채택 전에 checklist 를 고치면 안 되기 때문이다.
둘 다 갱신되지 않은 채 회차가 끝나면 다음 회차에 어긋난다.

**저장소의 `SKILL.md` 는 진단 회차에 고치지 마라.** 설치본과 md5 가 달랐다면
그 사실만 기준선에 적고, 어느 쪽으로 맞출지는 사용자가 정한다.

**순서를 지켜라: ① push → ② 재clone 확인(md5 대조) → ③ 그다음에 채팅 보고.**
채팅 보고를 먼저 길게 쓰면 세션이 끊길 때 저장소에 아무것도 남지 않는다.

**클라우드에서 push 가 막히면 PC 에서 push 해라.** 다른 스킬 점검에서 클라우드
컨테이너의 git 프록시가 403 을 내거나 샌드박스 분류기가 토큰이 들어간 push 명령
자체를 차단한 사례가 있다. 재시도해도 안 된다. 절차:
  1. 갱신할 파일을 사용자 폴더(`$HOME/mnt/claude/`)에 내려놓는다
     (어차피 "파일로도 내려줘" 요건이다)
  2. `device_bash` 로 사용자 PC 에서 clone → 파일 교체 → commit → push
  3. push 후 remote 설정에 토큰이 남지 않았는지 확인하고 작업용 clone 은 지운다

**진단 전문을 파일로도 내려줘. 채팅 요약본 말고 파일 자체가 필요하다.**
요약만 받으면 다음 세션으로 옮길 때 절반이 유실된다.

토큰을 못 받았으면 push 를 건너뛰되 **두 파일을 반드시 파일로 내려주고**
"저장소에 반영되지 않았다"고 명시해라. 완료라고 말하지 마라.
